# 规格书：GitHub 驱动的开源应用市场

## Problem Statement

目前缺少一个以 GitHub 为唯一分发源头、全自动化运营的 Android 开源应用市场。开发者发布应用需要依赖第三方商店后台、人工审核或自建分发系统，来源不可追溯、元数据易过期、门槛高；应用商店维护者需要投入大量人工进行收录、信息整理与质量把关；用户难以快速判断应用的来源可信度、开源状态、所需特殊权限（ADB / Root 等）与质量等级。

本系统要解决的核心问题：让应用收录、信息采集、评级、分发全流程自动化，同时保证来源可追溯、元数据零人工维护、质量分等清晰、客户端同步轻量。

## Solution

整个系统由三个 GitHub 仓库与五个 CICD 工作流构成：

- 应用市场客户端仓库：应用市场 App 自身的源码仓库，公开开源，是商店的“原住民”；客户端不收录于自身的应用列表，自更新走独立逻辑（内置自身仓库地址，静默查询最新 Release）。
- 承载仓库（应用列表仓库）：唯一的分发索引源头，每个应用独占一个文件夹（apps/&lt;owner&gt;/&lt;repo&gt;/），内含三个文件——app.json（用户手写：仓库地址、是否开源、最低特殊权限、一句话简介、可选 upstream）、app-info.json（工作流自动生成：完整采集元数据，含系统分配的应用 ID）、README.md（工作流自动拉取的原仓库 README）。APK 二进制不入承载仓库、不入聚合包，始终留在开发者自己的 GitHub Release 中，用户请求下载时客户端直连拉取。开发者通过 Fork 承载仓库、编写 app.json、提交 PR 即完成收录申请；已有应用的修改仅限初始上传者与应用仓库 Owner。
- 推荐页内容仓库：仅由维护者一人维护，不开放 Fork/PR 收录。维护者改动推荐内容后，CI 立即生成增量包 + 全量包 + 增量包解析路径；客户端对推荐包的更新时机与更新方式与应用列表聚合包完全相同。

五个工作流：工作流 1（PR 文件范围与修改权限校验）、工作流 2（应用核验与信息采集）、工作流 3（月度推荐票计票）、工作流 4（应用列表聚合 Release 分发，每日 5 次定时检查）、工作流 5（版本扫描：定期扫描全部收录应用的最新 Release，有新版本自动更新元数据）。

客户端应用（本工作区 Android 项目，UI 由柠檬音乐 SPICaMusic 移植）通过聚合包同步元数据（不预推 APK），页面为推荐、全部、搜索、设置四个一级页与详情、关于两个二级页；GitLink 作为底层下载底座，承载聚合包、推荐包与 APK 的全部下载链路。

## User Stories

1. 作为开发者，我想通过 Fork 承载仓库并提交 PR 来发布我的 Android 应用，以便不需要任何后台系统和人工审批。
2. 作为开发者，我想只填写一个轻量 JSON（仓库地址、是否开源、最低特殊权限、一句话简介）即可完成收录申请，以便发布成本最低。
3. 作为开发者，我不需要自己准备图标、名称、权限、README 等元数据，以便减少重复劳动并保证信息一致。
4. 作为开发者，当我误改或创建了自动生成的 app-info.json / README.md 时，我想收到带明确原因的 PR 关闭留言，以便修正后重新提交。
5. 作为开发者，当我的声明与实际不符（假开源、无 Release、Release 无 APK、无 README）时，我想立即得知具体失败点，以便补齐条件后再来。
6. 作为维护者，我想在 PR 创建时自动校验改动范围（只允许动 app.json），以便保护自动生成文件不被篡改。
7. 作为维护者，我想对已有应用的修改限定为初始上传者与应用仓库 Owner，以便防止无关人员改动他人的应用条目。
8. 作为维护者，我想自动核验“真开源/假开源”，以便将空壳仓库、假开源仓库挡在门外。
9. 作为维护者，我想在合并 PR 时自动生成 app-info.json 并拉取 README 入库，以便商店数据零人工维护。
10. 作为维护者，我想通过聚合 Release（全量包 + 增量包 + 解析清单）自动分发元数据，以便客户端轻量同步。
11. 作为维护者，我想对每个收录应用自动评级（A-E 五级），以便应用质量一目了然。
12. 作为用户，我想按等级筛选和排序应用，以便快速找到高质量可信应用。
13. 作为用户，我想在应用详情中看到开源状态与最低特殊权限（无 / ADB / Root），以便判断应用是否适合我的设备。
14. 作为用户，我想在列表中通过一句话简介快速了解应用是做什么的，以便不点开详情也能筛选。
15. 作为用户，我想阅读应用完整的 README 介绍，以便深入了解项目后再决定是否安装。
16. 作为用户，我想直接下载来自开发者 GitHub Release 的 APK，以便来源可追溯、可核验，且不在我请求前被推送。
17. 作为用户，我想看到 APK 校验和与来源 Release 信息，以便确认文件完整性与真实性。
18. 作为客户端，我想通过聚合包增量同步元数据，以便流量与启动开销最小。
19. 作为维护者，我想工作流可安全重跑且幂等，以便偶发失败不会产生脏数据或重复收录。
20. 作为开发者，我想通过同样的 PR 流程更新已有应用（指向新的 Release），以便所有变更都有记录可追溯。
21. 作为用户，我想每月提交一次推荐票（ISSUE），提名我认为值得晋升的开源应用，以便社区参与评级。
22. 作为维护者，我想每月自动收到推荐票数前 2~3 名的应用审核通知，以便社区驱动的评级晋升零人工统计。
23. 作为用户，我想每次打开应用时后台静默同步增量包、首次使用时前台阻塞下载全量包，以便无需任何手动刷新操作。
24. 作为用户，我想在推荐页看到卡片流（应用集合、博客文章等类型的卡片），以便发现优质内容。
25. 作为维护者，我想版本扫描工作流自动发现收录应用的新 Release 并更新其元数据，以便商店内版本信息不过期。
26. 作为客户端，我想通过内置自身仓库地址独立检查更新（不收录于自身应用列表），以便应用市场 App 自身保持最新。
27. 作为用户，我想通过应用详情中的“查看上游应用”入口快速跳转到本应用分支/Fork 自的上游项目，以便理解衍生关系。

## Implementation Decisions

### 系统组成与职责边界

系统由三个仓库、五个工作流与一个客户端组成。承载仓库负责应用收录元数据、README 与聚合发布物；推荐页内容仓库负责推荐卡片数据与推荐包发布；五个 CICD 工作流分别负责 PR 校验、核验与采集、推荐票计票、聚合分发、版本扫描；客户端负责面向用户的浏览、同步与下载。各部分通过明确的文件约定和 GitHub API 契约衔接，互不耦合。

### 承载仓库布局约定

每个应用独占一个文件夹，文件夹内含三个文件。app.json 由开发者编写并随 PR 提交，字段由人维护；app-info.json 由 CICD 自动生成，人工不得触碰；README.md 由工作流 2 从开发者仓库拉取原文写入，同样属于自动生成文件。承载仓库不存放 APK 二进制，APK 始终位于开发者仓库的 Release 资产中，app-info.json 记录其下载地址与校验信息。文件夹结构为 apps/&lt;owner&gt;/&lt;repo&gt;/，即应用仓库的 GitHub 全名 owner/repo 两级目录（工作流 1 校验目录名与 app.json 声明的仓库地址一致），与应用系统 ID 解耦。

### app.json（用户文件）字段

包含：repo（仓库地址，标准 GitHub 全名 owner/repo 格式，要求与所在目录 apps/&lt;owner&gt;/&lt;repo&gt;/ 一致，工作流 1 校验）；是否开源（布尔声明值，将由工作流独立核验）；最低特殊权限（应用运行所需的最低特殊权限，取值 none / adb / root，其中 Shizuku 依赖 ADB 通道激活，归入 adb 档，可多选，缺省为 none）；简介（一句话左右，用于列表页展示，让人一看就明白应用是做什么的）；upstream（可选，上游应用系统 ID——当本应用是某个已收录开源项目的分支或 Fork 时填写，客户端详情页据此展示“查看上游应用”入口；无分支/Fork 关系时省略）。该文件是工作流 1 与工作流 2 的唯一人工输入。文件不包含 id：应用 ID 由系统自动生成（见 app-info.json 字段），用户无法编辑修改。

### app-info.json（自动生成文件）字段

包含：id（系统自动生成的数字串，应用唯一标识，生成后永久不变、用户无法编辑；生成规则：合并 PR 时以当前仓库内最大 ID 递增分配，起点 1001；聚合包与推荐卡片统一用 id 引用应用）；upstream（继承 app.json，可选，指向另一应用的系统 ID）；应用包名（packageName，APK 的 applicationId，与 id 解耦——id 是商店内稳定标识，包名可能随版本变动）；显示信息（应用名称、图标引用）；权限列表（应用声明的全部权限，来自开源仓库清单或 APK 解包结果）；版本信息（versionName、versionCode、来源 Release tag）；来源信息（仓库 owner/repo、开源核验结论、APK 下载地址、APK SHA-256 校验和）；README 状态（已入库 / 无 README 已被拒绝，正常收录时恒为已入库）；维护者信息（uploader：初始上传者的 GitHub 账号，首次收录时固定记录，永久不变）；评级（grade 的当前值，可能被人工调整覆盖）；生成信息（生成时间戳、生成工作流标识）。该文件是客户端展示、权限校验与聚合包抽取的权威数据源。

其中 APK 下载地址字段为固化链接：采集时解析开发者仓库最新 tag 的 Release 资产写入，指向当时的最新版本；后续开发者发布新 Release 时，由工作流 5（版本扫描）定期发现并自动更新该字段与版本信息，无需开发者重提 PR。

### 工作流 1：PR 文件范围与修改权限校验

触发于 PR 创建或同步。规则一（文件范围）：本次改动仅允许新增或修改 apps/&lt;owner&gt;/&lt;repo&gt;/ 下的 app.json；创建或修改 app-info.json、README.md 即视为违规。规则二（目录与引用校验）：新增应用时目录路径必须为合法的 owner/repo 结构（owner 与 repo 均为 GitHub 合法命名），且与 app.json 声明的 repo 字段完全一致；upstream 若填写必须指向已存在应用的系统 ID。规则三（修改权限）：针对已有应用文件夹的改动，PR 作者必须等于该应用的初始上传者（app-info.json 的 uploader 字段）或该应用仓库的当前 Owner（以 PR 校验时 GitHub API 查询结果为准，仓库转移后按新 Owner 判定）；新增应用对作者不作限制。任何违规处理：关闭该 PR，并在 PR 上留言，明确指出违规点与原因。应用 ID 为系统字段，不受用户 PR 影响（新增应用在合并时由工作流 2 分配）。

### 工作流 2：应用核验与信息采集

输入为 PR 中的 app.json。核验链依次为：应用仓库存在且可访问；若声明开源则核验“真开源”（依据规则集：存在有效 LICENSE、源码真实非占位、仓库未被归档等）；检查最新 Release 存在且其资产中包含 APK 文件；检查仓库存在 README 且可拉取（无 README 即视为仓库不合格，直接拒绝）。核验链任一步失败：关闭 PR、写明关闭理由并留言告知。核验通过后进入信息采集：开源应用从仓库侧获取图标、名称、权限列表；非开源应用从最新 Release 下载 APK，解包提取图标、名称、权限；解析最新 tag 的 Release 资产取得 APK 下载地址（固化写入 app-info.json）；拉取 README 原文写入应用文件夹的 README.md。随后实时抓取 Star 数完成算法评级（E/D/C），并为新收录应用分配系统 ID（以当前仓库内最大 ID 递增，起点 1001）；采集结果、README、系统 ID 与评级在合并 PR 时由 CICD 落盘（app-info.json 与 README.md）并提交入库。

### 应用评级 A-E（定稿）

评级由“算法初评 + 人工调整”两层构成，等级定义：E 级为普通闭源应用；D 级为普通开源应用与较优质闭源应用；C 级为社区认可度高的开源应用（原则上不允许闭源进入，特别优质的闭源可由维护者破例给 C）；B 级为某一方面表现突出的开源应用（不允许闭源进入）；A 级为各个方面均表现突出的开源应用。

算法初评规则（自动、合并 PR 生成快照时实时抓取 Star 数）：开源应用 Star 数达到阈值（10k，可配置）评定 C 级，未达到评定 D 级；闭源应用一律评定 E 级，算法无权干涉闭源评级。算法唯一变量是 Star 数，不存在存疑状态，抓取失败即重新计算。

人工调整规则：C 级以上（B/A）全人工评级，社区推荐票是唯一触发通道——每个账号每月可提交一次推荐票（以 ISSUE 形式，固定模板加专属标签，编辑不改投，重复提交作废），工作流 3 每月初统计票数，前 2~3 名自动 @ 维护者进入审核；入选只代表获得审核资格，最终 B 或 A 由维护者逐个判断。闭源应用不参与推荐票，其晋升（D 级，特别优质可破例 C 级）由维护者主动调整。维护者可直接下调任何应用的评级，无需记录与公示。

评级变更路径仅两条：合并 PR 时随 app-info.json 快照重算，以及维护者的人工调整；不设定时全量重扫。评级角色为展示标签兼列表排序/筛选权重，不设硬性准入门槛（准入由工作流 2 核验链把关）。

### 工作流 3：月度推荐票计票

每月初触发。统计上月携带推荐票标签的 ISSUE，按应用聚合票数，生成票数前 2~3 名的应用名单并 @ 维护者进入人工评级审核。计票规则与防刷规则见人工调整规则。

### 工作流 4：应用列表聚合 Release 分发

每天固定间隔运行 5 次（约每 4 小时一次，定时触发，独立于其他工作流）。每次检查全市场所有应用（app.json + app-info.json 抽取出的所需字段）是否有变化。变更判定：每天首次运行时，任一应用元数据有变更（新收录、版本更新、评级调整、字段修改等）即触发发布，此时重新生成完整聚合包（全量包）；当天后续运行时，仅当变更量达标——新增应用 1 个即触发（任何新增都算），或发生变更的应用达到 2 个及以上——才触发发布，生成增量包（与上一期全量聚合包的差异补丁）；任何一次运行若无变更则不发布。聚合包仅含元数据，绝不含 APK。每次发布在承载仓库创建独立 Release，资产三件套：全量包（完整元数据）、增量包（二进制差异补丁，首次发布不生成）、解析清单（patch.json，记录基础版本、目标版本、补丁算法、增量包与全量包校验和，客户端按此应用补丁）。旧聚合 Release 保留不删，可回溯。

### 工作流 5：版本扫描自动更新

定期触发（频率与触发方式待定，倾向每日定时，独立于其他工作流）。扫描全部被收录应用：解析每个应用 app.json 指向仓库的最新 Release tag 与资产，与 app-info.json 中记录的版本信息对比；发现新版本（新 tag 或新 APK 资产）时，自动更新该应用的 app-info.json（版本信息、APK 下载地址固化链接、SHA-256 校验和，必要时重新采集图标/名称/权限），不要求开发者重提 PR。更新结果进入工作流 4 的变更判定，随下一次聚合发布同步给客户端。评级不随版本扫描变动（评级仅随 PR 合并与人工调整两条路径变更）。

### 推荐页内容仓库（第三仓库）

仅由维护者一人维护，不开放 Fork/PR 收录流程。内容为推荐卡片流，卡片类型为可扩展集合（第一版含应用集合 collection、博客文章 article，type 字段由仓库端扩展、客户端按类型渲染分支，类型清单可扩展，未知类型由旧客户端安全降级为占位展示，向前兼容不崩溃）。

展示形态（已定稿，App Store Today 布局）：推荐页为全宽沉浸大卡上下堆叠（屏宽 − 32dp，卡高约 230dp，大圆角，无头部结构）。每张卡片四要素：左上分类标签（label，小字，如“编辑精选/开源精选/文章”）、底部大标题（title，粗体大字，可换行）、标题下副标题（subtitle，应用数/作者等）、卡片背景（background，灵活多样——纯色 color、渐变 gradient、封面大图 cover 三种内置形态均可，字段与取值见数据契约；全部随推荐包下发，客户端不从 GitHub 拉取任意内容）。应用集合卡片不将应用图标平铺在卡面，点整卡进入集合页（头顶缩略大卡复用同卡背景 + 应用列表，复用全部页列表行，点击行进应用详情）；文章卡片点整卡进入内置阅读页（正文为 Markdown，随包下发，离线可读）。

数据契约（已定稿）：推荐仓库目录结构为 cards/（每卡一个 JSON 文件，文件名 NN-slug.json，NN 为两位序号即展示顺序）、articles/（文章正文 Markdown，articles/&lt;slug&gt;.md）、covers/（封面大图，covers/&lt;slug&gt;.png，建议 16:9、≤512KB）。卡片 JSON 统一字段：type（collection/article）、slug（本卡唯一标识）、label、title、subtitle、background（缺省时客户端用默认深色渐变兜底；color = 单个十六进制色值；gradient = 两个色值的数组，可追加扩展；cover = covers/ 下的文件名）、publish_date（可选，展示用日期文案）；collection 卡额外含 apps 字段（应用系统 ID 数组，引用承载仓库 app-info.json 的 id，客户端经聚合包按 id 反查应用元数据与图标；某 id 在聚合包缺失时显示占位图标仍保留条目）；article 卡额外含 article 字段（articles/ 下文件名）。卡片顺序 = cards/ 文件名序号。

维护者改动仓库内容后，CI 立即生成增量包 + 全量包 + 增量包解析路径（patch.json），发布形态与应用列表承载仓库的聚合 Release 一致（三件套资产）。推荐包格式：zip 归档，内含 index.json（卡片元数据数组，展开顺序）与 assets/（articles/ 与 covers/ 全部文件）；增量包复用与聚合包相同的二进制差异与 patch.json 机制（客户端 SyncEngine 同一套逻辑处理 AppIndex 与 Discover 两个通道）。客户端对推荐包的更新时机与更新方式与应用列表聚合包完全相同（开屏静默增量、首启/损坏时前台全量），两者并行独立。

### 客户端应用（本工作区 Android 项目）【主体已对齐，UI 细节待对齐】

页面结构：推荐、全部、搜索、设置四个一级页，详情、关于两个二级页。推荐页为 Today 风格全宽大卡流（应用集合、博客文章等类型卡片，见推荐页内容仓库章节）；全部页为应用列表（一句话简介 + 评级 + 特殊权限标识，可按等级筛选/排序）；搜索页搜索应用；详情页展示图标、名称、完整信息、README、权限列表与下载按钮，含“查看上游应用”入口（当 upstream 存在时）；设置页与应用信息页沿用既有结构。

数据同步（已定稿）：无手动刷新按钮。每次打开应用时自动检查聚合包是否有新的增量包：有则解析解析清单（patch.json）的增量路径，按路径逐个下载增量包并应用，全程后台静默执行；首次使用时下载全量包并在前台阻塞式完成；聚合包异常（校验失败/损坏）时兜底下载全量包。

下载链路（已定稿）：GitLink 作为整个客户端的底层下载底座，聚合包（增量/全量/解析清单）、推荐包、APK 下载全部复用 GitLink 的分块加速、断点续传、镜像等底层能力，不另起下载实现。APK 遵守三不原则——不入承载仓库、不进聚合包、不在用户请求前推送；用户点击下载时才由客户端经 GitLink 从 app-info.json 的 APK 下载地址（固化链接，指向开发者仓库 Release 资产）拉取，下载完成校验 SHA-256 后允许安装。

客户端自身更新（已定稿）：客户端是开源项目但不收录于自身应用列表。客户端内置自身 GitHub 仓库地址，打开应用时静默查询自身最新 Release 并与本地版本对比，发现新版本即提示下载更新（下载同样走 GitLink）；该逻辑与应用列表/推荐包的同步完全并行、互不依赖。

UI 构成（部分对齐）：整体 UI 从柠檬音乐（SPICaMusic，本工作区源码）移植，组件、大框、布局可沿用；音乐专属页面（播放器、专辑、艺术家、歌单、收藏、全部歌曲、歌词、音效、频谱、扫描等）移除。具体页面映射、组件复用范围与视觉细节待后续对齐。

### 健壮性要求

工作流全部幂等且可安全重跑；对 GitHub API 限流、Release 资产缺失、APK 损坏、JSON 校验失败、补丁校验和不一致等异常路径给出明确、可读的失败信息；关闭 PR 的留言必须包含可操作的修正指引。

## Testing Decisions

主测试接缝放在“校验与采集逻辑”上：将工作流 1 的文件范围与修改权限校验、工作流 2 的开源核验与信息采集、评级算法（Star 阈值判定）、工作流 3 的计票逻辑、工作流 4 的变更判定/聚合打包逻辑与工作流 5 的版本扫描判定实现为独立 CLI 工具，GitHub Actions 只做薄封装调用。这样可以用本地样例仓库与样例 JSON 直接测试 CLI 行为，无需真跑 CI。客户端侧接缝放在数据层：Repository 对聚合包解析、补丁应用、版本比较与 GitHub API 的测试用 JVM/Robolectric 完成，Compose UI 用 UI 测试覆盖。

好测试的判据：只断言外部行为，即给定输入（JSON 内容、仓库状态、Release 资产、Star 数、推荐票 ISSUE 集合、变更集合）后断言输出（校验结论、关闭动作与留言内容、生成的 app-info.json 字段、评级结果、月度计票名单、是否触发发布与发布物内容），不测内部实现细节。

现有先例：工作区模板已自带 app/src/test 与 androidTest 结构，可直接沿用；CLI 逻辑采用脚本自测加样例 fixture 的通用做法。

## Out of Scope

支付、评论、账号、推送等商店增值功能；非 Android 平台应用收录；在承载仓库内托管 APK 二进制或经聚合包向设备预推送 APK；评级的定时全量重扫、公开申诉与争议流程（人工调整不记录不公示，开发者无申诉通道）；PR 自动合并的决策（合并动作由人工或维护策略决定）；客户端推荐票入口（推荐票仅通过 GitHub ISSUE 形态存在，客户端不提供入口）；承载仓库与各 CICD 的具体实现细节（除本规格已定稿的命名与结构外）。

## Further Notes

定稿说明（v0.4）：三仓库结构（客户端源码仓库、承载仓库、推荐页内容仓库）与五工作流已确认。应用目录结构为 apps/&lt;owner&gt;/&lt;repo&gt;/（仓库全名两级目录），与应用系统 ID 解耦；应用 ID 由系统自动生成（数字串，递增分配起点 1001，永久不变），用户无法编辑，app.json 不包含 id，upstream 字段引用上游应用系统 ID；推荐页数据契约定稿（cards/ 每卡一文件 + articles/ + covers/，background 三形态：color/gradient/cover，缺省默认渐变兜底，collection 卡 apps 引用系统 ID，推荐包为 index.json + assets 的 zip，增量复用 patch.json 机制）；客户端不收录于自身应用列表，自更新走独立逻辑。客户端无手动刷新：开屏静默增量、首启前台全量、异常兜底全量。GitLink 底层化为聚合包/推荐包/APK 全部下载链路。app-info.json 的 APK 下载地址为固化链接，由工作流 5 版本扫描定期发现新版本自动更新，评级不随版本扫描变动。UI 整体沿用柠檬音乐 SPICaMusic 组件、大框与布局，音乐专属页面移除。

术语约定：承载仓库（应用列表/分发索引仓库）、推荐页内容仓库（第三仓库，单人维护）、app.json（用户文件/申请文件）、app-info.json（自动生成文件/元数据文件）、应用系统 ID（系统自动生成的数字串，应用唯一标识，用户不可编辑）、upstream（上游应用系统 ID 引用）、工作流 1（PR 校验）、工作流 2（核验与采集）、工作流 3（月度推荐票计票）、工作流 4（聚合 Release 分发）、工作流 5（版本扫描自动更新）、真开源（经规则集核验通过的开源声明）、聚合包（全市场应用元数据的抽取集合）、解析清单（patch.json，增量包应用说明）、卡片流（推荐页的卡片式内容流，卡片类型含应用集合、博客文章等）、GitLink（底层下载底座，承载聚合包/推荐包/APK 全部下载）。
